# Native sponsored placements

This component funds and publishes a bounded sponsored index on NEAR. An active row is a stored native placement whose fixed publisher transfer succeeded. It does not measure human impressions, reach, clicks, conversions, acquisition, sales, or revenue. It is a NEAR-native equivalent; external ad platforms are not required.

The implementation is an unaudited candidate. Local/offline fixtures and actual sandbox acceptance are separate evidence. No public promotion deployment, account, credential, or transaction has been exercised by the implementation agent. Consult the final verification report for the actual acceptance status; unit fixtures alone do not establish live operation.

The independent reader uses `active` for paid, unexpired, unstopped entries and `list`/`campaign` for public history. Stopping a campaign hides its active placements, prevents new placements, and preserves past records. The standalone owner entry is `web-chain/native-promotion.html`.

## Authority and source binding

A deployment has immutable owner, restricted operator public key, publisher, native feed/code hash, and company. All three monetary roles are distinct. The owner directly funds an exact typed campaign: native post ID/content SHA-256, fixed per-placement price,1–8 placements, and expiry within seven days. Public/nonsecret, rights, and placement-only acknowledgements are separate. The commitment also binds every immutable role/source pin and deployment address.

The owner client and worker read the promotion/feed/company code, actual company owner, and original immutable post at one FINAL block. They independently recompute the feed's exact canonical content hash, including company code and media commitments. The contract commits those references; it does not query or cryptographically attest another account's code or company ownership. RPC/finality and the pinned contract implementation remain trusted boundaries. Any full-access key holder able to replace a contract can change its implementation; an owner role by itself does not prove custody of that upgrade key.

Only the exact receiver-scoped operator key may call `place`, with zero deposit. The runtime requires the onchain access key to permit only `place`, with a positive finite allowance within the owner's configured cap. It cannot fund, change price/payee/source/owner/policy, stop, refund, install dependencies, or call providers/models. Contract caps include64 campaigns,8 placements per campaign, at most64 placements per chain day, at most512 lifetime placements, and at most64NEAR of lifetime accepted campaign budgets. The configured daily/lifetime limits can be lower. Refunds, failures and freeze/resume never reset those counters.

## Money and uncertainty

Funding attaches exactly two separate amounts: a retained32768-byte storage contribution at the actual protocol price, and price × maximum placements as escrow. Storage is neither refundable nor withdrawable. It is not business cash, sales, or profit. Gas is separately paid and reported from complete actual FINAL receipt graphs; no provider USD invoice or conversion is invented.

Each new sequential slot reserves its exact price and permanent identity before one transfer to the immutable publisher. A private callback records paid or known failed. Pending/ambiguous transfers cannot be retried, refunded, or declared paid. Repeating a reserved/completed slot returns its existing record and creates no second transfer. A known failed publisher payment consumes its slot/counters and restores budget credit. Failed-transfer funds may return after the callback, so an owner refund additionally checks actual account solvency; credit alone is insufficient.

After stop, expiry, or exhaustion of slots, the owner can request all remaining available escrow back to the original owner account only. A refund has one in-flight identity; a known failed refund allows at most three explicit same-amount attempts in total. Pending/unknown refunds have no retry route. Publisher payments already completed are not refunded. Conservation is enforced as accepted budget = available + payment pending + paid + refund pending + refunded. Deployment backing pays storage and operational gas separately.

## Worker and owner recovery

`executor/native_promotion_client.mjs` is the shipped restricted worker path. Importing it performs no IO. Its default public transport is disabled unless the protected owner configuration explicitly enables one of the two fixed testnet RPC URLs; there is no endpoint fallback or automatic retry, and no mainnet factory is enabled. Public request starts are paced by at least1000ms, each fetch/body is bounded by12s/4MiB, and each command has85s/64-request limits. The explicit local-sandbox factory verifies loopback, chain/genesis and exact account/code/source identities.

The credential and journal loaders require canonical absolute paths, private owner directories, regular non-symlink single-link files, and bounded bytes. Secrets never enter command arguments, logs, exports, or browser state. The worker saves/fsyncs canonical signed Borsh bytes, hash, nonce, reference block and exact zero-deposit action before its sole SDK `sendTransaction` call. Signed evidence is limited to32KiB, its envelope64KiB, and the active journal1MiB. `FinalizedJournal` and `commitFinalOutcome` enforce existing durable archives and complete receipt/fee graphs. Startup validates saved evidence before any RPC. Reconciliation reads only the original pending hash and never resends saved bytes; it remains possible after the original key's allowance is exhausted. A journal lock has no automatic stale takeover.

The CLI accepts a protected config path and one bounded JSON command on stdin: `inspect`, `place`, or `reconcile`. Configure the exact fields declared by `CONFIG` in the runtime; no secret value is accepted on the command line. Public execution requires separate owner configuration and an actual FINAL funded campaign/key permit. Recording fixtures cannot activate the public factory. Tests may monkeypatch the HTTP function to examine production mechanics; that is explicitly synthetic transport evidence, not public-chain proof.

The owner browser journals only the exact public action and transaction metadata. Public post text and account keys are not stored in that journal. Wallet lookup/account inspection completes under an original epoch/review/draft guard before the synchronous durable dispatch boundary. Cancel/Escape before that boundary creates no pending write. After wallet dispatch starts, any missing hash or lost acknowledgement retains the original request across reload, with no automatic resubmission. Reconciliation checks exact method/arguments/gas/deposit, owner/receiver, complete FINAL receipts and an execution block after the original review. The browser fixture uses seeded Node-only keys and is not evidence of an extension-wallet or hosted service.

## Validation entry points

- `node --test integration/native_promotion_contract.test.mjs` exercises the actual TypeScript in a synthetic host, including failed/unknown callbacks and budget conservation. It is not a NEAR protocol test.
- `node --test executor/test_native_promotion_client.mjs` exercises the installed SDK against recording RPC fixtures, durable unknown/restart, protected files, scope denial, pacing, and signed-evidence tampering.
- `node --test web-chain/tests/native-promotion-actions.test.mjs` checks the actual feed-producer hash formula, owner approvals, wallet cancellation/ABA/mutation, and original FINAL outcomes.
- `node integration/native_promotion_e2e.mjs` is the actual isolated NEAR/Chrome acceptance. It uses the real native feed, shipped worker, native publisher/refund receipts, independent index reads, and unknown wallet recovery. Its report is accepted only after source checks and owned browser/server/chain teardown. Failed fixtures and logs are retained.

Only the native feed's current bounded routes are referenced: public text/company-page paragraphs, PNG images/boards, and silent AVC MP4 short/channel videos within16KiB. The promotion index does not generate media or change that content. JPEG, arbitrary links/HTTP destinations, external social/ad APIs, targeting based on personal data, audience tracking, and measured acquisition experiments are unsupported here.

The [NEAR RPC provider table](https://docs.near.org/api/rpc/providers), [asynchronous callback rules](https://docs.near.org/smart-contracts/anatomy/crosscontract), and [storage accounting guidance](https://docs.near.org/smart-contracts/security/storage) explain the transport, callback and storage boundaries. A one-second client pace is a local bound; the public provider's numeric free-tier limit is unpublished and no service guarantee is implied.
